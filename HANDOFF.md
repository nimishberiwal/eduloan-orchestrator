## 0. Read-me-first: how to work on this codebase

Six rules that will save the next session from breaking things:

1. **`src/data/seed.ts` holds 14 hand-written applications (APP-2601…APP-2614).
   Never edit those literals.** They back the acceptance checklist and the
   clearance-committee demo. When you add a field to `Application`, make it
   *required on the type, optional on `AppSpec`, and defaulted inside `mkApp()`*
   so the 14 literals keep compiling untouched.
2. **Re-walk `docs/ACCEPTANCE.md` after every change**, not just at the end.
   Items 4 and 5 are the fragile ones — item 4 asserts two validation messages
   render *verbatim*, item 5 asserts APP-2608's collateral buckets and its
   `CHECKLIST_REGENERATED` audit event.
3. **Rule text, codes and messages render verbatim.** Reviewers read them on
   screen and compare against the BRD. Don't paraphrase, don't "improve" copy.
4. **`stage` / `status` / `owner` / `blocker` are four independent dimensions.**
   Never collapse them into one field. A file can be at S07, in progress, owned
   by Credit, and blocked on a third party — all at once.
5. **Verify, don't assert.** This project has caught several real defects
   (a clipped popover, HITL false positives, an unreachable classifier label)
   only because claims were checked in the browser. `window.__eduloan.store` is
   exposed in dev for exactly this.
6. **Prototype, front-end only.** No backend, no router, no persistence. All
   state lives in one Zustand store and resets on reload.

## 1. What it is

A **back-office loan origination orchestration dashboard** — the internal screen
where bank staff run education-loan applications through their lifecycle. Built
for an internal **product-clearance committee** to review the journey design.

- **Product**: Education Loan — Abroad Postgraduate, **USA only**
- **Borrower**: the student (no income). **Credit spine**: the parent
  co-applicant. Optional third party: a collateral provider / guarantor.
- **Ticket**: up to **₹1,00,00,000**
- **Audience**: Sales, Ops, Credit, Risk, Compliance, Admin — plus a
  **customer mirror** showing what the applicant sees at each stage.

It is deliberately *not* a customer-facing journey. It is the orchestration
layer: queues, gates, deviations, maker-checker, SLA, audit.

### Provenance — three layers of requirements

The build happened in three waves, and knowing which wave a feature came from
explains most of the design:

| Wave | Source | What it added |
|---|---|---|
| **v1** | A self-contained master build prompt (18 sections) | The whole spine: state machine, roles, document buckets, 60 validations, 14 seed apps, 4 views, an 18-point acceptance checklist |
| **v2** | 10 items of reviewer feedback | CRM, per-stage anomaly rules, in-application deviations, peer view, batch mode, ₹ rollups, report exports, rejection insights, per-stage filters, escalation matrix |
| **v3** | The user's own source BRDs (BRD-18/19/20/21 + a cumulative Document Checklist) | Document sourcing modes, consent artifacts, validations to 73 with BRD traceability, HITL queue, classification confidence, CAM analytics, policy corrections |

v3 is the important one: the dashboard was originally built from a *synthesised*
prompt, then retrofitted to the *real* BRDs it should have been derived from.

## 4. Domain model

```ts
type StageId   = 'S01'…'S13'
type TerminalId = 'DISBURSED_ACTIVE' | 'REJECTED' | 'WITHDRAWN' | 'EXPIRED'
type Stage     = StageId | TerminalId

type Department = 'Sales' | 'Ops' | 'Credit' | 'Risk' | 'Compliance' | 'Admin'
type BlockerKind = 'none' | 'customer' | 'bank' | 'third_party'

type DocLifecycle  = 'requested' | 'uploaded' | 'fetched' | 'extracted' | …
type DocMandate    = 'M' | 'C' | 'O'          // mandatory / conditional / optional
type PartySection  = 'applicant' | 'co_applicant' | 'collateral' | 'loan'

type SourcingMode = 'manual_upload' | 'consent_fetch' | 'auto_fetch'
                  | 'bank_generated' | 'internal'

type Severity           = 'BLOCK' | 'WARN' | 'INFO'
type ValidationStatus   = 'pass' | 'fail' | 'waived' | 'pending'
type RuleApplicability  = 'in_scope' | 'conditional' | 'out_of_scope_us_only'
```

`DocSource` (`'Upload' | 'DigiLocker' | 'API' | 'Manual' | 'CKYC'`) is
**deprecated** — superseded by `SourceSystem` + `SourcingMode`. It is retained
only so old literals compile; the Documents grid reads `sourceSystem`.

### The four independent dimensions (repeat of rule 4 — it matters most)

- **`stage`** — where in the journey (S01…S13 or a terminal)
- **`status`** — in progress / pending checker / on hold / …
- **`owner`** — `{ department, officer, officerId? }`
- **`blocker`** — `{ kind, detail? }` — who the file is actually waiting on

Every view slices on these separately. Collapsing any two produces a dashboard
that lies about the pipeline.

## 5. State machine — 13 stages

| ID | Stage | Owner | Note |
|---|---|---|---|
| S01 | Registration | Sales | Record created post OTP; APP ID minted |
| S02 | Application capture | Sales | Personal, course, university, admit status, ask, intake, co-applicant |
| S03 | KYC | Ops | **Parallel per party**: applicant lane + co-applicant lane |
| S04 | Document collection | Ops | Dynamic checklist; blocker usually `customer` |
| S05 | Document verification | Ops | Per-doc QC + extraction; intra-doc validations |
| S06 | Bureau & financial analysis | Credit | CIBIL both parties, AA banking, 4-way income convergence, FOIR |
| S07 | Underwriting | Credit | Eligibility, tier slotting, overlay check, deviations |
| S08 | Risk & fraud review | Risk | PEP/sanctions, fraud screen; Compliance clears manual hits |
| S09 | Collateral processing | Ops | **Conditional (Tier-3 only)**; legal ∥ technical valuation, runs alongside S07–S08 |
| S10 | Credit decision | per DoA | APPROVE / APPROVE-WITH-CONDITIONS / DECLINE / REFER; maker-checker |
| S11 | Sanction & acceptance | Credit | Sanction letter, validity clock starts, processing fee, acceptance |
| S12 | Documentation | Ops | Loan agreement e-sign, e-stamp, NACH mandate (penny-drop) |
| S13 | Disbursement | Ops | **Repeating tranche sub-journey**, per-tranche gates |

**Terminals**: `DISBURSED_ACTIVE`, `REJECTED`, `WITHDRAWN`, `EXPIRED`.

### Parallelism

S03–S09 are not a straight line. Three lanes run concurrently and **converge**
before S07:

- **Lane A · Applicant** — KYC → Documents → Verification
- **Lane B · Co-applicant** — KYC → Documents → Bureau
- **Lane C · Collateral** — C1 KYC & net worth → C2 Title/asset →
  C3 Legal & valuation → C4 Charge creation

The Journey Timeline component renders this literally, including per-lane
failure marks (acceptance item 3: APP-2603 has Lane B failing at eKYC).

### Forward gates

`FORWARD_GATES` in `data/stages.ts` maps each stage exit to the validation IDs
that must be `pass` or `waived`. Two gates are **non-overridable in every role**:

- **S03 (KYC)**
- **S08 (AML / sanctions)**

No role sees a skip control on those — the move-forward modal shows
"⛔ Non-overridable gate". Every other gate can be passed by **raising a
deviation**, which is the modelled form of an override (there is no raw
"force forward" verb).

`gating.isResolved()` treats a **missing** validation as resolved. This is
load-bearing — it is what makes the "lite fidelity" bulk seed safe (§13).

### The reconciliation story (read this before touching `buckets.ts`)

v3's first pass treated the BRD checklist as an **overlay** — it hung sourcing
metadata on the catalogue that already existed and filled three obvious gaps.
It never reconciled **row by row**. Result: 113 dashboard rows against 125
checklist rows, with the master prompt's **merged** rows still in place.

The merges were the real problem, not the count. The checklist gives AACSB,
ABET, ABA and LCME each their own row because they are four different bodies
with four different lookups — one merged "programmatic accreditation" row cannot
carry four sources or four classifier labels.

Rows split during reconciliation: Form 60 · school transcripts · Class-12
migration certificate · one-time charges ×2 · the four named accreditors +
a catch-all · lender approved-list vs Premier-PG overlay doc · FD/LIC/MF/G-sec
as four securities · foreign account vs forex card. Labels were also changed to
the checklist's own wording.

**Splitting exposed a live defect**: with one merged row,
`/Programmatic accreditation/` bound *everything* to
`PROGRAMMATIC_ACCREDITATION_AACSB`, and ABA/LCME fell through to
`GENERIC_UPLOAD` — three of the BRD's four label constants were unreachable.

## 9. Sourcing & consent (the v3 headline)

Every document names **only** its `SourceSystem`. The sourcing mode and consent
requirement are **derived** from it through the `data/sources.ts` registry (32
sources), so the two can never drift apart. This was a deliberate choice: hand-
typing both fields on 126 templates guarantees they disagree eventually.

**Five modes, each with real operational meaning:**

| Mode | Meaning | Blocker implication |
|---|---|---|
| `auto_fetch` | Public registry / verification lookup, no consent | `bank` — it's a bank task |
| `consent_fetch` | Fetchable, gated on a customer consent artifact | `customer` (consent) |
| `manual_upload` | The customer must provide it | `customer` (upload) |
| `bank_generated` | Lender or panel vendor produces it | `third_party` |
| `internal` | Internal policy table | none |

"Waiting on the customer" now distinguishes a missing **consent** from a missing
**upload** — operationally different problems with different nudges.

**Seven consent artifacts** (`data/consents.ts`), each with `grantedBy`,
`unlocks[]`, `mechanism`, `validityDays`:

| Consent | Granted by |
|---|---|
| Aadhaar eKYC (UIDAI) | applicant |
| Central KYC registry | applicant |
| DigiLocker | applicant |
| Account Aggregator — banking | co_applicant |
| Income Tax / TRACES | co_applicant |
| GSTN returns | co_applicant |
| Credit bureau (CIBIL / CIC) | co_applicant |

Granting a consent **auto-fetches every in-scope document** (`requested` →
`fetched`) and writes **one audit line per consent, not per document**.

Two invariants worth protecting:

- **`fetched` ≠ verified.** `fetched` sits alongside `uploaded` at the same
  standing; a fetched document still passes QC and extraction, so forward gates
  behave exactly as before. Auto-fetch must never fabricate verification.
- **A declined consent does not block the file** — the affected documents fall
  back to `manual_upload`.

Consent progression follows the journey: identity consents (Aadhaar / CKYC /
DigiLocker) around KYC, financial ones (AA / TRACES / GST / bureau) at credit
analysis.

## 10. Validation engine — 73 rules

`data/validations.ts`. **73 defined · 70 evaluate · 3 out-of-scope.**

| Tier | Count | Meaning |
|---|---|---|
| `VAL-INT-*` | 22 | Intra-document (a single document is internally consistent) |
| `VAL-CRS-*` | 27 | Cross-document (two documents agree) |
| `VAL-EXT-*` | 24 | External (a document agrees with an authoritative source) |

**Out of scope (`out_of_scope_us_only`)**: `VAL-EXT-22`, `VAL-EXT-23`,

```ts
export const ALL_VALIDATIONS    = withBrd([...VAL_INT, ...VAL_CRS, ...VAL_EXT])
export const ACTIVE_VALIDATIONS = ALL_VALIDATIONS.filter(v => v.applicability !== 'out_of_scope_us_only')
```

### BRD traceability without renumbering

Dashboard IDs were **deliberately not renumbered** — the acceptance checklist
asserts two messages verbatim, and renumbering would break every reference.
Instead each rule carries a `brdRef` back to its BRD origin:

```ts
'VAL-INT-06' → 'V-INT-17'
'VAL-INT-07' → 'V-INT-18 · V-INT-21'
'VAL-EXT-09' → 'V-EXT-13 (BRD-21)'
'VAL-EXT-10' → 'V-EXT-13 (BRD-20)'
'VAL-CRS-n'  → 'V-CRS-n'          // the 27 cross rules already matched 1:1
```

> **⚠ Open issue for the BRD author.** `V-EXT-13` is defined **twice** in the
> source BRDs: BRD-20 uses it for the parent ITR/26AS live match; BRD-21 §6.3
> uses it for credential-evaluation verification. Both are operationally
> required for abroad PG, so **both are implemented** and disambiguated in the
> traceability matrix. This should be renumbered in the source BRD.

### Seeded, not computed

Rules are **seeded as data**, per the original spec. Each application carries a
per-rule status. Rules triggered at stages *after* the app's current stage are
seeded `pending`.

> **`pending` is ambiguous, and it caused a real bug.** A validation reads
> `pending` both when its outcome is genuinely awaited **and** when the file
> simply hasn't reached its trigger stage. The HITL credential-eval detector
> originally treated both the same and produced 6 false-positive cases (24 → 18
> after the fix). It now gates on `stageRank(app.stage) >= 7` first. **Any new
> detector reading `pending` must make the same distinction.**

Messages interpolate through `ValCtx`; `GENERIC_PASS_TOKENS` exists because raw
`{months}` / `{duration}` tokens once leaked into rendered pass messages.

## 11. HITL review queue

Seven triggers from BRD-21's pipeline `hitl` node (`data/hitl.ts`), each with
`title`, `question`, `owner`, `severity`, `brdRef`:

1. `programmatic_accreditation_unlisted` — accreditation claimed but not listed
2. `premier_overlay_borderline` — institution on the list, programme not
3. `credential_eval_pending` — evaluation pending or borderline
4. `sponsored_mba_verification` — sponsor verification
5. `test_optional_no_entrance` — test-optional admit with no entrance score
6. `existing_ug_el_exposure` — existing UG education loan, aggregate exposure
7. `conditional_admit` — clauses to review

**Cases are derived, not stored.** `lib/hitl.ts` recomputes the queue from live
application state on every render, so it can never go stale against the file.
**Only the officer's decision is persisted**, keyed `appId|trigger`.

Three concepts that are easy to conflate and must stay distinct:

- **HITL case** — "a person must look at this"
- **Deviation** — a catalogued policy exception, formally raised
- **Hold** — parked awaiting an external event

## 12. Document classification

`data/classification.ts` implements BRD §7's label vocabulary
(`GRE_SCORECARD`, `CREDENTIAL_EVAL_WES`, `PROGRAMMATIC_ACCREDITATION_ABET`,
`SPONSORSHIP_LETTER_MBA`, …) via `LABEL_RULES` (regex on the checklist name)
and `AMBIGUOUS`.

**Confidence is modelled, not randomised.** BRD-21's `reup-class` node names
exactly five genuinely ambiguous cases, and those are the five the classifier
flags low-confidence:

1. GRE-Subject vs GRE-General
2. Non-NACES credential evaluation
3. Programmatic certificate **without an accreditor identifier** ← the catch-all
   row only, after the accreditor split
4. Sponsor letter on individual letterhead
5. Non-English transcripts

A `requested` document has **no** classification — you cannot classify a file
that hasn't arrived.

## 13. Seed model

`buildSeed()` returns **legacy-first**: `[...the14, ...buildBulkSeed()]` — 214
applications total.

- **APP-2601…APP-2614** — hand-written, back the acceptance checklist
- **APP-2701+** — procedurally generated (deterministic **mulberry32** PRNG,
  fixed seed). IDs start at 2701 so they can never collide with `APP-26xx`.

**"Lite" fidelity** for generated apps: documents only for buckets gated at or
before the current stage; validations only for already-triggered rules. Safe
because `gating.isResolved()` treats a missing validation as resolved. A full
reseed of 214 applications costs **~20 ms**.

`resetDemo()` must clear: applications, automation log, approval queue,
fired-rule keys, escalations, filters, clock offset — **and three module-global

## 14. Automation, SLA, escalation

**17 per-stage rules** in `data/rules.ts`, IDs `R-S01-01`, `R-S02-01`, …
Each has a stage, a condition, and an action label
("Nudge for KYC completion", "Expire for inactivity", "Escalate to Ops Team Lead").

Safety model:

- **`autoRunEnabled` defaults `false`** — first load behaves exactly like v1.
- Non-destructive actions **auto-apply**; destructive ones (close / withdraw /
  reject) **queue for approval** and never auto-apply.
- `matchRules()` **hard-skips terminal stages**, so automation can never touch
  a closed file (this is what protects APP-2613/2614).
- A **`firedKey(ruleId, appId, stage)`** guard makes sweeps idempotent. Without
  it, a second sweep re-sends every nudge.

**SLA (`lib/escalation.ts`)**: assignment SLA is **48 h** with a **36 h** amber
warning, escalating up the officer hierarchy to the manager.

> **The SLA pauses when the blocker is `customer` or `third_party`.** It measures
> *bank-side responsiveness only*. Without this rule ~70 % of aged files read as
> breached and the escalation register is meaningless noise; with it, roughly
> **2 of the 12 open curated files** breach — and they are exactly the two the
> bank is actually sitting on. Do not "fix" this into a wall-clock SLA.

## 16. CSV export & the artifact download path

`lib/csv.ts` is the single choke point for handing the user a file.

- CSV is written with a **UTF-8 BOM (`﻿`)** — without it Excel mangles `₹`.
- Cells are guarded against **formula injection** on `= + - @`.

`downloadText()` delivers through `deliver()`, which branches:

```
published artifact  → await claude.use('downloads') → downloads.save({filename, data})
everywhere else     → ordinary blob + <a download> click
```

**Why**: the claude.ai artifact viewer blocks any download a page starts itself
(`<a download>`, data:/blob: hrefs, script-driven saves are all inert). Without
this branch every CSV export silently does nothing for anyone the link is
shared with — and report exports were called "very important" by the reviewer.

`csv` sits in the host's **extended** extension set and may not be enabled, so
an `extension_not_enabled` / `rejected_extension` rejection retries the same
bytes as `.txt`. A `declined` rejection is the viewer's call and is **never**
retried. The artifact must declare `capabilities: {downloads: true}`.

The dev server and standalone HTML are unaffected — no host, direct download,
byte-identical behaviour.

## 18. The frozen clock

`lib/clock.ts` owns "now". `BASE_NOW_ISO = '2026-07-20T10:00:00.000Z'`, frozen
so aging, TAT and sanction countdowns are deterministic and match the seed's
`daysInStage` values exactly.

An operator offset lets a demo advance time. **The offset is a module global**,
so `advanceClock` must also bump a `clockTick` counter that views subscribe to —
otherwise React sees no state change and the button appears to do nothing.
